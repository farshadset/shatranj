# تحلیل کامل پروژه: Realtime Chess Arena + Retro Digital Menu

## معرفی کلی
این پروژه در واقع تلفیقی از دو بخش اصلی است:
1. **Realtime Chess Arena** – یک بازی شطرنج آنلاین دو نفره با قابلیت اتاق‌سازی، زمان‌سنج، و ارتباط بی‌درنگ (SSE)
2. **Retro Digital Menu** – سیستم مدیریت منوی دیجیتال برای کافه/رستوران با قابلیت ویرایش لحظه‌ای و ذخیره‌سازی یکپارچه

ظاهراً این پروژه یک مونورپو است که هم شامل بازی شطرنج و هم منوی کافه می‌شود. اما در عمل، ساختار دایرکتوری بیشتر شبیه یک پروژه Next.js با بک‌اند Go برای شطرنج است، و فایل‌های مرتبط با منوی دیجیتال (مانند STORAGE_SYSTEM_README.md) نشان‌دهنده وجود سیستم مدیریت محتوا برای منو می‌باشد.

---

## بخش اول: Realtime Chess Arena

### ویژگی‌های موجود (Current Features)
- **اتاق‌های چندنفره بلادرنگ** با استفاده از SSE (Server-Sent Events)
- **ساخت/پیوستن به اتاق** با لینک قابل اشتراک‌گذاری
- **اعتبارسنجی حرکات قانونی** با موتور شطرنج (کتابخانه notnil/chess در Go)
- **تشخیص کیش و مات، تساوی، وقت اضافه، تسلیم**
- **ساعت شطرنج قابل تنظیم** (زمان پایه + افزایشی)
- **لیست حرکات زنده، هایلایت آخرین حرکت، پنل وضعیت بازیکنان**
- **رابط کاربری واکنش‌گرا با تم تیره**

### فناوری‌ها
- فرانت‌اند: Next.js 14, React 18, TypeScript, Tailwind CSS
- بک‌اند: Go 1.22+ (پوشه `go-server/`) با کتابخانه `github.com/notnil/chess`
- ارتباط بلادرنگ: SSE (`text/event-stream`)
- مدیریت فرآیند: PM2 (دو پردازه: web + api)
- پراکسی معکوس: Nginx

### APIهای بک‌اند Go
| متد | مسیر | توضیح |
|------|------|-------|
| POST | `/api/chess/rooms` | ایجاد اتاق |
| GET | `/api/chess/rooms/:roomId` | دریافت آخرین وضعیت اتاق |
| POST | `/api/chess/rooms/:roomId/join` | پیوستن به عنوان بازیکن یا تماشاگر |
| POST | `/api/chess/rooms/:roomId/move` | ارسال حرکت |
| POST | `/api/chess/rooms/:roomId/resign` | تسلیم شدن |
| GET | `/api/chess/rooms/:roomId/events` | آبونمان رویدادهای بلادرنگ (SSE) |
| GET | `/api/health` | سلامت و جزئیات اجرا |

### استقرار روی پارس‌پک (یا VPS دلخواه)
- فایل‌های آماده: `ecosystem.config.cjs`, `deployment/parspack/nginx-realtime-chess.conf`, `DEPLOYMENT.md`, `bootstrap.sh`
- بسته آفلاین داکر: `docker-bundle.sh` برای ساخت و انتقال در محیط‌های بدون دسترسی به رجیستری بین‌المللی

## بخش دوم: Retro Digital Menu (سیستم مدیریت منو)

طبق فایل `STORAGE_SYSTEM_README.md`، یک سیستم کامل ذخیره‌سازی یکپارچه برای مدیریت تغییرات منو و تنظیمات کافه وجود دارد.

### ویژگی‌های سیستم ذخیره‌سازی
- **تایید/لغو تغییرات** با ردیابی خودکار
- **گزینه‌های ذخیره‌سازی**: مرورگر (localStorage)، سرور (API)، ترکیبی (سرور اول و مرورگر به عنوان پشتیبان)
- **پشتیبان‌گیری و بازیابی** از طریق فایل JSON
- **پشتیبانی از بخش‌های**: آیتم‌های منو، دسته‌بندی‌ها، تنظیمات نوبار، بخش دسرها، قالب‌های نمایش، تنظیمات تم

### نحوه استفاده
- تنظیم متغیر محیطی `NEXT_PUBLIC_STORAGE_TYPE` (browser/server/hybrid)
- استفاده از `useUnifiedStorage` hook در کامپوننت‌ها
- دسترسی مستقیم از طریق `storageService`

### وضعیت فعلی (بر اساس تحلیل کدهای خوانده‌شده)
- سیستم ذخیره‌سازی به طور کامل مستند شده اما **مشخص نیست که آیا کاملاً پیاده‌سازی شده یا تنها مستندات آن وجود دارد**.
- فایل `package.json` نشان می‌دهد که وابستگی‌های Next.js و ابزارهای جانبی (تایپ‌اسکریپت، تیلویند، پلی‌رایت) وجود دارد، اما هیچ اشاره‌ای به سرور Go برای منو نیست (سرور Go فقط برای شطرنج است). بنابراین احتمالاً بک‌اند API برای ذخیره‌سازی منو هنوز پیاده‌سازی نشده و فقط مستندات آن آماده است.

## باگ‌ها و مشکلات احتمالی (Bugs & Issues)

بر اساس بررسی فایل‌ها و مستندات، موارد زیر به عنوان مشکوک یا نیازمند بررسی شناسایی شده:

1. **نقص در ابزار message** – طبق تست قبلی، فراخوانی ابزار message بدون فیلد `action` با خطا مواجه می‌شود. (این مربوط به محیط اجرای فعلی است، نه خود پروژه)

2. **یکپارچگی شطرنج و منو** – دو سیستم مجزا در یک مخزن قرار گرفته‌اند، اما مشخص نیست که چگونه با هم تداخل دارند. ممکن است مسیرهای API تداخل پیدا کنند.

3. **ذخیره‌سازی منو در حالت سرور** – مستندات API endpoints را برای ذخیره‌سازی معرفی کرده (`/api/save-data` و ...) اما چنین APIهایی در کد Go دیده نمی‌شود. احتمالاً این APIها باید در Next.js (مسیرهای `app/api/`) پیاده‌سازی شوند که در فایل‌های خوانده‌شده اثری از آنها نبود.

4. **عدم وجود فایل `.env` واقعی** – فقط `.env.example` موجود است، و متغیرهای حیاتی مانند `NEXT_PUBLIC_CHESS_API_BASE_URL` باید به درستی تنظیم شوند.

5. **مشکل احتمالی در اجرای همزمان دو سرور** – فرانت‌اند Next.js روی پورت 3000 و سرور Go روی 4000. اگر در محیط production از Nginx استفاده نشود، ممکن است CORS یا عدم دسترسی به API رخ دهد.

6. **مدیریت نشست‌های اتاق شطرنج** – در حالت `memory` (پیش‌فرض) با ری‌استارت سرور، تمام اتاق‌ها از بین می‌روند. مستندات اشاره به `CHESS_STORE_MODE=memory` و TTL دارد، اما گزینه پایدارتر (مثل Redis) پیاده‌سازی نشده.

7. **تست‌ها** – وجود `playwright.config.ts` نشان می‌دهد تست‌های E2E نوشته شده‌اند، اما خروجی تست‌ها یا پوشش آن مشخص نیست.

8. **نقص در مستندات راه‌اندازی سریع** – فایل `README.md` اصلی دستور `npm run go:run` را معرفی کرده، اما در `package.json` چنین اسکریپتی ممکن است تعریف نشده باشد (بررسی نشد).

## جمع‌بندی
این پروژه یک سیستم نسبتاً پیشرفته با دو قابلیت اصلی است. قسمت شطرنج عملیاتی‌تر به نظر می‌رسد و قابلیت استقرار دارد. قسمت منوی دیجیتال بیشتر در سطح مستندات و طرح است و نیاز به پیاده‌سازی بک‌اند دارد. برای راه‌اندازی سریع، ابتدا متغیرهای محیطی را تنظیم کرده و سپس سرور Go و Next.js را اجرا کنید. در صورت وجود باگ در ابزار message (که مربوط به این چت است) جای نگرانی نیست.

در صورت نیاز به رفع باگ‌ها یا پیاده‌سازی ویژگی‌های جدید، لطفاً اولویت خود را مشخص کنید.
